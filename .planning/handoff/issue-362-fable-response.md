# Issue #362 — audit response (Fable, read-only; HEAD 28b14a1 vs tag v2.1.10)

Evidence base: line-by-line read of the named suspects + `include/udphelper.h`, `main/radiomoduleconnector.cpp`, `main/streamparser.cpp`, `main/metrics.cpp`, `main/crash_blackbox.cpp`, `main/system_reset.cpp`, `main/ping_service.cpp`, `main/main.cpp`, sdkconfig deltas; delegated sweeps of `settings.cpp`/`webui_storage.cpp` (buffer writes) and of every service unit that touches sockets (syslog, log_stream, events, prometheus, monitoring, mqtt, webui*, reset_info, led, pushbutton). Static only; "inference" marked where not proven from code.

## Findings

1. **Net-watchdog self-heal cannot fire in a tcpip wedge — it joins the amplification.** `main/monitoring.cpp:1392` `int rtt_ms = ping_service_ping(gw_str, NET_WATCHDOG_PING_TIMEOUT_MS);` → `main/ping_service.cpp:100` `esp_ping_new_session()` → `socket(AF_INET, SOCK_RAW, …)` → `tcpip_api_call` with no timeout (core locking off). Once `tcpip_thread` stops, `heap_watchdog_task` parks forever inside `socket()` before any ping timeout applies; the low-heap restart, the "net watchdog" diagnostic and `crash_blackbox_snapshot_now()` (`:1410/:1419`) are all behind it. Only works for MAC/PHY/ARP wedges where tcpip still services API calls. Post-dates the field failures (ec542c9), so not the initiator. Severity: High for the mitigation, none as initiator. Secondary: `:1393` treats every negative return (incl. `PING_SERVICE_INTERNAL` = calloc/socket/task-create failure) as "gateway unreachable" → 5 socket-exhaustion failures with link up ⇒ restart misattributed to the network (Low).

2. **tcpip thread executes the whole log-capture chain per dropped datagram.** `main/rawuartudplistener.cpp:696-698` `if (xQueueSend(queue, &event, 0) != pdPASS) { ESP_LOGW(TAG, "UDP queue full, dropping packet");` runs in lwIP context → `main/log_manager.cpp:268` `xSemaphoreTake(_mutex, pdMS_TO_TICKS(10))` (≤10 ms sleep while httpd holds the mutex in `getLogSnapshot` `:346-370`: `heap_caps_get_largest_free_block` + `resize(≤8 KB)` + memcpy) → subscribers (`main/syslog.cpp:215-221` malloc(392)+`xQueueSend(…,0)`+free; `main/log_stream.cpp:363` `StreamItem it` = 272 B on the *logging task's* stack + `xQueueSend(…,0)`) → `:89` second full `vprintf` to the console, which is UART0 **without a driver** (`main/main.cpp:132-133` only `uart_param_config/uart_set_pin`; VFS `uart_tx_char` busy-waits on the 128 B FIFO ⇒ ~9 ms per 100-char line at 115200). Effect: under a queue-full burst tcpip (prio 18) is throttled to UART speed and briefly sleeps on an app mutex; all bounded, never a stop. Stack (inference): lwIP RX depth + esp_log + `log_vprintf` `buf[256]` (`:79`) + subscriber frames + newlib `vfprintf` ≈ 1.9–2.2 KB of `CONFIG_LWIP_TCPIP_TASK_STACK_SIZE=3072`; no end-of-stack watchpoint configured (only `FREERTOS_CHECK_STACKOVERFLOW_CANARY`), so a sparse overrun would corrupt the heap block allocated just before the stack — in `tcpip_init` that is the tcpip mbox itself. Not the delta: v2.1.10 ran an equal-or-heavier capture path unconditionally (`v2.1.10:src/main.cpp:184` `LogManager::begin(8192)`, `v2.1.10:src/log_manager.cpp` did a `vsnprintf(NULL,0)` probe + format + `vprintf`), and the same `ESP_LOGW` existed at `v2.1.10:src/rawuartudplistener.cpp:330`. Active only with system-log capture, syslog or a live-log WS client. Severity: Low (stall amplifier / diagnostic noise), initiator only under the stack inference.

3. **Latent lwIP-lifetime hazard in two unused stop paths.** `main/ntpserver.cpp:147` `vTaskDelete(_tHandle);` and `main/radiomoduleconnector.cpp:118` `vTaskDelete(_tHandle);` delete tasks that call `pbuf_alloc/pbuf_free` (hold `g_lwip_protect_mutex`) and `tcpip_api_call` (per-thread lwIP semaphore in FreeRTOS TLS, freed by the deletion callback — `CONFIG_FREERTOS_TLSP_DELETION_CALLBACKS=y`). A delete while the victim holds the lwIP protect mutex leaves tcpip blocked forever at its next `SYS_ARCH_PROTECT` — exactly the silent-wedge signature. Grep of `main/` shows **no runtime caller** of `NtpServer::stop()` or `RadioModuleConnector::stop()`; the only network stop wired into `full_system_restart` is `RawUartUdpListener::stop()`, which is cooperative (no forced delete, `:535-541`). Severity: latent only; cannot be today's initiator.

4. **MQTT stop-watchdog reboots from the 2 KB FreeRTOS timer daemon.** `main/mqtt_handler.cpp:337-342` `ESP_LOGE(...); ResetInfo::storeResetReason(...); emergency_network_stop_before_reboot(); esp_restart();` in a timer callback (`CONFIG_FREERTOS_TIMER_TASK_STACK_DEPTH=2048`, prio 1): `main/reset_info.cpp:92` `NvsStorageLock storage_lock(portMAX_DELAY, …)` + NVS flash write, then `esp_eth_stop`. Unbounded lock wait stalls every software timer; the last-resort reboot can itself hang. Not a tcpip corruptor; MQTT is a closed feature. Severity: Medium for recovery, informational here.

5. **INTLEVEL holders (question 2).** App side, every `portMUX` user enumerated: `main/systemclock.cpp:63/92/111` (16-byte struct copy), `main/webui_ota.cpp:115-117` (`memcpy` 128 B), `:131-134` (`snprintf` ≤128 B into caller buffer) — µs each, nothing blocking inside. Only ISR-context app code: `main/dcf.cpp:126` (closed) and `main/crash_blackbox.cpp:801-805` IRAM tick hook (two IRAM loads + one RTC-slow-mem store). No `esp_timer` ISR dispatch, no `esp_intr_alloc`, no `xTaskAbortDelay`. IDF paths this firmware exercises: lwIP `SYS_ARCH_PROTECT` is the recursive mutex `g_lwip_protect_mutex` (not a spinlock); `heap_caps_get_largest_free_block/heap_caps_get_info` (`main/crash_blackbox.cpp:706-709`, `main/log_manager.cpp:346`, heap_watchdog) walk every TLSF block under the multi_heap `portMUX` — sub-ms on a 250 KB heap; `ledc_*`, `gpio_*`, UART driver spinlocks are register-scoped. **No spinlock held across a blocking call found anywhere in the exercised app or IDF surface.** The only exercised IDF path that legitimately parks a core at INTLEVEL ≥1 for long is the spi_flash cache-disable cross-core spin (closed by brief). Inference for the 6.1 escalation: the mechanical bridge from a silent heap/lifetime corruption to an IWDT is `portENTER_CRITICAL` on a `portMUX_TYPE` whose owner word was overwritten (FreeRTOS queues, semaphores, TCBs and mboxes carry their spinlock inside heap objects) — `spinlock_acquire` spins without timeout at INTLEVEL when the owner reads as the other core; a non-core garbage value asserts instead (assertions are enabled: `CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_ENABLE=y`), so a clean IWDT with no assert implies the corrupted word looked like a held lock or the holder was a task that died while spinning on a second lock.

## Best candidate

No concrete initiator exists in the audited delta: every 2.2.x change on the lwIP-facing surface (raw-uart listener, NTP server, `udphelper.h`, log ring, DNS cache, settings/webui_storage) is bounded and, where it differs from v2.1.10, strictly tighter (pcb creation moved into `tcpip_api_call`, `pbuf_copy_partial` instead of `pb->payload` aliasing, non-blocking queue posts, cooperative stop, `_activeSenders` Dekker gate; verified in `main/rawuartudplistener.cpp:353-405, 505-556, 639-664, 678-703`). If forced to name the single most likely app-side contributor it is Finding 2's log-capture chain executing inside the tcpip thread (stall amplifier + unmeasured stack budget on a 3072 B stack with no end-of-stack watchpoint), but the same path ran unconditionally and stably in v2.1.10, so the evidence points outside the brief's suspect list — either an IDF/lwIP-internal path or a hardware/EMAC condition — rather than at a 2.2.x wild write. Finding 3 is the only code in the tree that *could* produce the exact "tcpip blocked forever, scheduler alive, no panic" signature, and it is unreachable at runtime today.
